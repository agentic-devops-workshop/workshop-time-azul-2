# ADR-004 — Estratégia de Testes em Camadas

**Data**: 20/05/2026
**Status**: ✅ Aceita
**Decisores**: Par 3 (Technical Lead + Developer) + Par 4 (QA Engineer)

## Contexto

O SIFAP legado não possui testes automatizados — a validação era feita manualmente por operadores em ambiente de homologação. O SIFAP 2.0 precisa de uma estratégia de testes que:

- **Garanta equivalência** com o comportamento legado (mesmas entradas → mesmas saídas)
- **Cubra regras regulatórias** (descontos, cálculos, conciliação CNAB 240)
- **Rode em CI** sem depender de infraestrutura externa
- **Seja implementável em 8 horas** (workshop constraint)

A stack-alvo define JUnit 5 + Testcontainers (backend) e Vitest + Testing Library (frontend).

## Decisão

Adotaremos **testes em 3 camadas**, priorizando de dentro para fora:

### Camada 1 — Testes Unitários (obrigatórios)

- **Ferramenta**: JUnit 5 + Mockito (backend), Vitest (frontend)
- **Escopo**: Domain services puros — cálculos, validações, regras de negócio
- **Cobertura mínima**: 70% de linhas nos pacotes `domain/` e `application/`
- **Rastreabilidade**: Todo teste tem comentário `// REQ-XXX` no cabeçalho
- **Exemplos**: validação CPF Módulo 11, teto de desconto 30%, faixas de contribuição social

### Camada 2 — Testes de Integração (obrigatórios para módulos de dados)

- **Ferramenta**: JUnit 5 + Testcontainers (PostgreSQL 16)
- **Escopo**: Repositories JPA, migrations Flyway, queries complexas
- **Cobertura**: Cada entidade JPA tem pelo menos 1 teste de persistência
- **Container**: PostgreSQL 16 via Testcontainers — sem banco externo necessário

### Camada 3 — Testes de Componente / API (desejáveis)

- **Ferramenta**: Spring Boot `@SpringBootTest` + `MockMvc`
- **Escopo**: Endpoints REST — request/response + status codes
- **Cobertura**: Cada endpoint da tabela de contratos tem pelo menos 1 teste happy-path + 1 erro

### Frontend

- **Ferramenta**: Vitest + Testing Library
- **Escopo**: Componentes com lógica de negócio (formulários, validação client-side)
- **Não testar**: Componentes puramente visuais (shadcn/ui wrappers)

## Opções Consideradas

### Opção 1: Testes em 3 camadas (escolhida)

- **Vantagens**: Cobertura progressiva; roda em CI sem infra; Testcontainers garante paridade com produção
- **Desvantagens**: Setup de Testcontainers adiciona ~30s ao build

### Opção 2: Somente testes unitários

- **Vantagens**: Mais rápido de implementar; sem dependência de Docker no CI
- **Desvantagens**: Não valida persistência JPA, migrations Flyway nem endpoints REST

**Rejeitado por não cobrir camada de dados — risco alto para mapeamento Adabas→PostgreSQL.**

### Opção 3: Testes end-to-end com Playwright

- **Vantagens**: Testa fluxo completo do usuário
- **Desvantagens**: Frágil; lento; requer frontend funcional antes de rodar; não cabe em 8h

**Rejeitado por incompatibilidade temporal e fragilidade.**

## Consequências

### Positivas

- Cada regra de negócio migrada tem teste de equivalência
- CI falha se cobertura cair abaixo de 70%
- Testcontainers garante que JPA mappings + migrations funcionam antes do deploy

### Negativas

- Docker precisa estar disponível no runner de CI (GitHub Actions tem por padrão)
- Testcontainers adiciona ~30s ao tempo de build
- Manter `// REQ-XXX` nos testes exige disciplina (CI pode validar via grep)
