# ADR-002 — Mapeamento de Dados Adabas → PostgreSQL

**Data**: 20/05/2026
**Status**: ✅ Aceita
**Decisores**: Par 2 (Enterprise Architect + Software Architect) + Par 4 (DBA)

## Contexto

O legado SIFAP usa 4 DDMs Adabas com campos MU (múltiplos valores) e PE (grupos periódicos) — estruturas que não existem diretamente em bancos relacionais. Precisamos mapear essas estruturas para PostgreSQL 16 com JPA/Hibernate, mantendo a semântica de negócio.

DDMs legados:
- **BENEFICIARIO (ARQ 150)** — 22 campos, incluindo MU (DESCONTOS) e PE (DEPENDENTES com 5 campos cada)
- **PAGAMENTO (ARQ 160)** — 15 campos
- **PROGRAMA-SOCIAL (ARQ 155)** — 12 campos
- **AUDITORIA (ARQ 170)** — 10 campos, append-only

Desafios específicos:
- Campos MU (ex.: `DESCONTOS`) precisam virar relação 1:N em tabela filha
- Grupos PE (ex.: `DEPENDENTES`) com sub-campos precisam virar entidade própria com FK
- Campos Adabas packed decimal → `BigDecimal` no Java / `NUMERIC` no PostgreSQL
- Datas Adabas no formato `YYYYMMDD` como inteiro → `DATE` ou `TIMESTAMP`

## Decisão

Adotaremos **mapeamento direto com normalização**, onde cada DDM vira um schema PostgreSQL e cada campo MU/PE vira tabela filha.

### Regras de mapeamento

| Adabas | PostgreSQL | JPA |
|--------|-----------|-----|
| Arquivo (ARQ) | Schema | `@Table(schema="...")` |
| Campo simples | Coluna | `@Column` |
| Campo MU | Tabela filha 1:N | `@OneToMany` + `@JoinColumn` |
| Grupo PE | Tabela filha com FK | `@OneToMany(cascade=ALL)` |
| Packed decimal | `NUMERIC(15,2)` | `BigDecimal` |
| Data YYYYMMDD | `DATE` | `LocalDate` |
| Super-descriptor | Índice composto | `@Index` |

### Schemas

```sql
CREATE SCHEMA beneficiary;
CREATE SCHEMA payment;
CREATE SCHEMA audit;
CREATE SCHEMA admin;
```

Cada módulo só acessa seu próprio schema. Cross-schema joins são proibidos — comunicação via interfaces de domínio.

### Exemplo: BENEFICIARIO (ARQ 150) → beneficiary schema

```
BENEFICIARIO (Adabas)          →  beneficiary.beneficiaries (PG)
├── CPF (campo simples)        →  cpf VARCHAR(11) UNIQUE NOT NULL
├── DESCONTOS (MU)             →  beneficiary.discounts (tabela filha)
│   ├── TIPO-DSCT              →  type CHAR(1)
│   └── PCT-DSCT               →  percentage NUMERIC(5,2)
└── DEPENDENTES (PE)           →  beneficiary.dependents (tabela filha)
    ├── NOME-DEP               →  name VARCHAR(60)
    ├── CPF-DEP                →  cpf VARCHAR(11)
    ├── PARENTESCO             →  kinship CHAR(2)
    ├── DT-NASC-DEP            →  birth_date DATE
    └── SEXO-DEP               →  gender CHAR(1)
```

## Opções Consideradas

### Opção 1: Mapeamento direto com normalização (escolhida)

- **Vantagens**: Semântica relacional clara; JPA mapeia naturalmente; queries SQL padrão
- **Desvantagens**: Requer mais tabelas que o Adabas original

### Opção 2: JSON columns para MU/PE

- **Vantagens**: Menos tabelas; preserva estrutura aninhada
- **Desvantagens**:
  - Queries de busca em campos internos exigem operadores JSON (mais lentos)
  - Perda de integridade referencial
  - JPA não oferece suporte nativo (exige custom type)

**Rejeitado por perda de integridade referencial e complexidade de queries.**

### Opção 3: Migração para MongoDB (documento)

- **Vantagens**: MU/PE mapeiam naturalmente para arrays e subdocumentos
- **Desvantagens**:
  - Stack adicional (MongoDB) — fora da toolchain aprovada (PostgreSQL 16)
  - Time sem experiência
  - Transações multi-documento são complexas

**Rejeitado por estar fora da stack aprovada.**

## Consequências

### Positivas

- Modelo relacional clássico — todo o time conhece SQL
- JPA/Hibernate mapeia 1:1 sem hacks
- Flyway gerencia migrations versionadas
- Integridade referencial garantida pelo banco

### Negativas

- Mais tabelas que o Adabas original (4 DDMs → ~10 tabelas)
- JOIN necessário para reconstruir visão "completa" de beneficiário
- Migration inicial requer mapeamento cuidadoso de tipos numéricos (packed decimal)
