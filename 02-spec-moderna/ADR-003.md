# ADR-003 — Autenticação via OAuth2/OIDC + JWT

**Data**: 20/05/2026
**Status**: ✅ Aceita
**Decisores**: Par 2 (Enterprise Architect + Software Architect) + Par 5 (DevOps)

## Contexto

O legado SIFAP usa autenticação por login/senha hardcoded no Natural (sem expiração, sem rotação, sem MFA). O SIFAP 2.0 precisa de autenticação moderna que atenda:

- **LGPD** — rastreabilidade de quem acessou dados pessoais (CPF)
- **TCU/CGU** — auditoria de ações por operador identificado
- **Segurança** — OWASP Top 10 compliance (A07:2021 — Authentication Failures)
- **Governo Federal** — integração com Gov.br como IdP quando disponível

Perfis de acesso identificados no legado:
- **OPERATOR** — cadastra beneficiários, gera pagamentos, consulta
- **ADMIN** — configura programas sociais, gerencia usuários
- **AUDITOR** — consulta trilha de auditoria (somente leitura)

## Decisão

Adotaremos **OAuth2/OIDC** com **JWT** para autenticação e autorização:

### Arquitetura

```
┌─────────┐     ┌──────────┐     ┌─────────────┐
│ Frontend │────→│ Gov.br   │────→│ Backend API │
│ Next.js  │ ←── │ (IdP)    │ ←── │ Spring Sec  │
└─────────┘     └──────────┘     └─────────────┘
                      ↑
              ┌───────┴───────┐
              │   Keycloak    │  (dev/staging only)
              │   (local IdP) │
              └───────────────┘
```

### Detalhes técnicos

1. **Produção**: Gov.br como Identity Provider (OpenID Connect)
2. **Dev/Staging**: Keycloak local (Docker Compose) com mesmos scopes e claims
3. **JWT** com claims customizados: `role` (OPERATOR, ADMIN, AUDITOR), `cpf` (mascarado)
4. **Spring Security** com `@PreAuthorize` para RBAC por endpoint
5. **Token**: Access Token (15min) + Refresh Token (8h — turno de trabalho)
6. **Azure**: Managed Identity para comunicação serviço-a-serviço (sem secrets)

### Mapeamento de roles

| Perfil legado | Role JWT | Permissões |
|---|---|---|
| Operador SIFAP | `OPERATOR` | CRUD beneficiários, gerar ciclo, consultar pagamentos |
| Administrador | `ADMIN` | Tudo de OPERATOR + gerenciar programas e usuários |
| Auditor TCU/CGU | `AUDITOR` | Somente leitura em trilha de auditoria |

## Opções Consideradas

### Opção 1: OAuth2/OIDC + JWT (escolhida)

- **Vantagens**: Padrão de mercado; integra com Gov.br; stateless; auditável
- **Desvantagens**: Setup inicial de Keycloak para dev

### Opção 2: Session-based (HttpSession + Cookie)

- **Vantagens**: Simples de implementar; familiar
- **Desvantagens**:
  - Stateful — não escala horizontalmente sem sticky sessions ou Redis
  - Não integra com Gov.br (OIDC)
  - CSRF mais complexo de mitigar

**Rejeitado por incompatibilidade com Gov.br e escalabilidade.**

### Opção 3: API Key por operador

- **Vantagens**: Extremamente simples
- **Desvantagens**:
  - Sem expiração automática
  - Sem MFA possível
  - Sem padrão de auditoria de identidade
  - Não atende OWASP A07

**Rejeitado por não atender requisitos de segurança.**

## Consequências

### Positivas

- Autenticação stateless — escala horizontalmente sem sessão compartilhada
- Integração futura com Gov.br é "trocar o issuer URL" no Spring Security
- Cada ação é rastreável ao CPF do operador (claim no JWT)
- Keycloak local garante paridade dev/prod

### Negativas

- Keycloak adiciona container ao Docker Compose (+ ~512MB RAM)
- Configuração inicial de realm/client/roles requer setup script
- Token expirado durante operação longa pode causar UX ruim (mitigação: silent refresh)
