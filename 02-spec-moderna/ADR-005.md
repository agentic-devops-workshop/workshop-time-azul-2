# ADR-005 — Strangler Fig para Coexistência Legado/Moderno

**Data**: 20/05/2026
**Status**: ✅ Aceita
**Decisores**: Par 2 (Enterprise Architect + Software Architect)

## Contexto

O SIFAP legado (Natural/Adabas) roda há 29 anos e não pode ser desligado de uma vez. A migração precisa ser incremental:

- **Operadores** continuam usando o SIFAP legado para módulos ainda não migrados
- **Módulos migrados** devem funcionar de forma independente no SIFAP 2.0
- **Dados** precisam fluir entre legado e moderno durante a transição
- O workshop constrói um **protótipo completo** mas o go-live seria incremental

O padrão **Strangler Fig** (Martin Fowler) resolve exatamente este cenário.

## Decisão

Adotaremos o padrão **Strangler Fig** com as seguintes regras:

### Fases de Migração

```
┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│   Fase 1     │    │   Fase 2     │    │   Fase 3     │
│  Coexistência│ →  │  Migração    │ →  │  Desligamento│
│              │    │  Progressiva │    │              │
│ SIFAP legado │    │ Módulos em   │    │ SIFAP 2.0    │
│ + SIFAP 2.0  │    │ paralelo     │    │ completo     │
│ lado a lado  │    │              │    │              │
└──────────────┘    └──────────────┘    └──────────────┘
```

### Ordem de Migração (Módulos)

1. **Beneficiary** — menor risco, dados cadastrais estáveis
2. **Payment** — maior valor, regras complexas
3. **Audit** — depende de Beneficiary + Payment
4. **Admin** — transversal, por último

### Regras de Coexistência

- **Facade/Proxy**: Um API Gateway roteia chamadas — módulos migrados vão para SIFAP 2.0, demais continuam no legado
- **Sincronização**: Batch noturno ETL (legado → PostgreSQL) para dados de módulos não migrados
- **Read-only mirror**: Durante a Fase 2, o SIFAP 2.0 pode ler dados do legado mas só escreve nos módulos já migrados
- **Feature flags**: Cada módulo tem flag `sifap2.module.{name}.enabled` para rollback rápido
- **Cutover por módulo**: Quando um módulo é promovido, o legado para aquele módulo é desligado (não o SIFAP inteiro)

### No Workshop (Escopo Reduzido)

- Construímos **Fase 1 + início da Fase 2** como protótipo
- O ETL batch é simulado por um script SQL de seed
- Feature flags ficam em `application.yml` (não em serviço externo)
- API Gateway é simulado pelo Spring Boot routing (sem Kong/Nginx separado)

## Opções Consideradas

### Opção 1: Strangler Fig incremental (escolhida)

- **Vantagens**: Zero downtime; rollback por módulo; operadores não perdem acesso durante migração; alinhado com Modular Monolith (ADR-001)
- **Desvantagens**: Complexidade de manter dois sistemas em paralelo; sincronização de dados

### Opção 2: Big-bang — desligar legado e ligar moderno de uma vez

- **Vantagens**: Mais simples conceitualmente; sem período de coexistência
- **Desvantagens**: Risco extremo para sistema regulatório de 29 anos; sem fallback

**Rejeitado — inaceitável para sistema que processa pagamentos de benefícios sociais.**

### Opção 3: Reescrita paralela sem coexistência

- **Vantagens**: Código limpo desde o início
- **Desvantagens**: Time precisa replicar 100% das funcionalidades antes do go-live; não permite entregas incrementais

**Rejeitado — não permite validação progressiva com operadores reais.**

## Consequências

### Positivas

- Migração incremental com validação a cada módulo
- Operadores continuam trabalhando durante toda a transição
- Rollback granular via feature flags
- Alinhado com o Modular Monolith — cada bounded context migra independentemente

### Negativas

- Período de coexistência requer sincronização de dados
- Equipe precisa manter conhecimento do legado Natural até o desligamento final
- Testes de equivalência legado↔moderno são obrigatórios (ver ADR-004)
